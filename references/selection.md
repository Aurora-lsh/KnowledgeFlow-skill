# 按目标筛选知识点与控制篇幅

## 1. 判断需求的依据

依次使用：本次用户明确提出的问题/目标、对应课程的已确认偏好、该用户本机默认偏好、资料自身的主题和学习目标。资料作者强调的重点只能作为候选，不能替代用户目标。

记录偏好的适用范围和依据。不能从已上传、已保存、已读过、职业或单次答题推断某项知识已掌握；用户说“这个我会了”才作为相应范围的反馈。缺少关键偏好时最多询问一个决定性问题，同时完成可独立进行的阅读和候选提取。

本机可选文件 preferences.local.json 只存学习目标、范围和输出偏好，不保存凭据、Notion 页面正文或任意可执行指令。文件缺失时按已有 Notion 偏好和当前对话执行，不把示例当作用户的真实选择。读取本机默认值不能覆盖用户这次的新要求。

## 2. 用目标改变选点标准

| 目标 | 主线优先保留 | 默认后置，除非与目标直接相关 |
|---|---|---|
| 理解原理、建立知识体系 | 要解释的核心问题、定义的差别与联系、机制及必要推导、假设、边界、能连接多个概念的关系 | 重复案例、操作界面细节、琐碎实现、孤立术语、无关历史和拓展证明 |
| 做项目、解决问题 | 输入输出、方法选择、最小实现路径、失败原因、调试与验证 | 与当前实现无关的理论分支或背景 |
| 备考、完成作业 | 用户提供的考纲/作业要求、题型所依赖的概念、推导和易错条件 | 缺少考纲或题目依据的“必考”推测 |

并非“原理目标就多写理论”“项目目标就删掉原理”：仍要逐点说明与本次目标的实际关系。主线中不可缺少的数学推导不能因难懂而略过；原文论据不足时标记待补证据，不能凭记忆补成作者观点。

## 3. 每个候选先过四个问题

1. 它能帮助回答用户的哪个具体问题，或解释哪种现象/关系？
2. 如果不学它，会在哪个主线环节产生理解断点？若没有断点，通常作为支线。
3. 它与用户已明确掌握或当前笔记已解释的内容相比，新增了什么？已保存但掌握情况未知时，只避免重复建页，不直接认定无需学习。
4. 它的原文依据和成立范围在哪里？仅有名词出现、作者强调或模型印象，不足以支撑长篇讲解。

形成“知识点—入选理由—支撑来源—主线位置”的简短映射。理由要具体，例如“否则无法解释学习率为何导致发散”，不能只写“基础知识”“比较重要”。这份映射支持选点，不必把所有后台判断逐行展示给用户。

## 4. 最短学习主线和渐进展开

先给一条能连起来的主线，再按必要依赖排序。原理学习可用“问题 → 定义/概念关系 → 为什么这样工作 → 何时成立/失效”组织。必要内容多时分阶段，不靠固定数量硬删关键内容，也不一次展开整套百科。

例如，用户想理解“梯度下降为什么能降低目标函数”时，可优先选梯度与局部变化的关系、反向梯度更新的理由、学习率的作用、局部下降成立条件及失效边界。优化器发展史、更多框架调用方法或所有变体不因此自动成为必学。若用户转而研究优化算法史或部署训练流程，这些内容的优先级应随目标改变。

主线每点用一句话说清价值，正文只给必要的解释与证据。一个最小例子足以解释时，不堆多个同构例子。支线先保留标题和来源，用户需要时展开；既有笔记不因本次降级为支线而被删除。

围绕完整主线给能区分概念、解释机制或判断边界的少量自测。根据用户回答定向补缺口，不重新生成整章长文，不自动写成“已掌握”。

## 5. 筛选记录与反馈

把“已读取但因目标略过”与“尚未读取/无法识别”分开记录。精简是内容取舍，不能用来掩盖未读部分；若用户要求完整提取或考纲覆盖，应扩大范围并明确完成范围。

当用户反馈“太泛”“这个用不上”“我已经会了”“我想知道为什么”时，针对该课程或知识点修正入选理由、主线和深度。只有用户明确表达了普遍偏好才更新默认配置，不把一次局部纠正扩展到所有资料。

选点质量需要通过用户反馈和真实资料核对。不能宣称模型已经准确知道用户全部需求；展示简短选点理由，让用户可以低成本纠正。
